# Ghost card applet

The Java Card applet for Ghost bearer cards, as `docs/bearer-card-spec.md`
describes it, for the NXP J3R180 (JCOP 4 P71) measured in
`docs/j3r180-measurements.md`. Java Card 3.0.5 Classic, with `int` support.

The card draws each fill's Phantom Key itself, computes the coin's F,
commitment, marker and sealed note exactly as Ghost's client does, signs seal
statements with an LMS key it made itself, and releases a fill's seed material
only to that fill's open code. No command returns the key, the card random,
the LMS private seed or the applet's code.

## Layout

| Path | What |
| --- | --- |
| `src/ghostcard/GhostCard.java` | The applet: commands, states, Ghost's hashes, the note seal, LMS, Open |
| `src/ghostcard/Nvm.java` | The applet's only path to persistent memory |
| `src/ghostcard/KeccakF.java`, `ChaCha.java`, `Poly.java` | Generated by `gen/` (the code measured on the J3R180) |
| `gen/` | The generators; `python3 gen/generate.py` rewrites the three files |
| `test/ghostcard/` | The tests on jcardsim |
| `test/tear/ghostcard/Nvm.java` | The tests' `Nvm`: the same writes, with a power cut at any of them |
| `test/vectors.txt` | Ghost's vectors, written by `core/tests/card_applet_vectors.rs` |
| `host/ghostcard/host/` | What a phone does: the command client, Ghost's derivations, statement and Open checks, and `RealCard`, the run on a real card |

## Building and testing

Needs JDK 17 and Apache Ant. The Java Card tools (the Oracle SDKs,
ant-javacard, jcardsim, Bouncy Castle) are fetched at pinned versions with
checked hashes into `~/.cache/card-applet`.

```
card-applet/build.sh    # builds build/ghostcard.cap and prints its code hash
card-applet/test.sh     # runs every test on jcardsim
```

The code hash is the SHA-256 of the CAP file's load file data block (its
components in load order), which is what the card receives. It does not cover
the zip around them, so the same source gives the same hash on every build;
CI builds twice and compares. The hash goes into each card's certificate.

The tests compile the applet from `src/` with one class swapped: `Nvm` is
replaced by the test version, which counts every persistent write and commit
and can cut the power at any one of them (rolling back the open transaction,
as the card does). For Make, Check, Open, Refill and loading, the tests cut the
power at every point in turn and check the card is left before or after the
command, never between. The test `Nvm` also fails any persistent write made
outside a transaction.

The vectors: `core/tests/card_applet_vectors.rs` computes, with Ghost's own
client at the commit the wallet pins, what Make must give for fixed card random,
writer nonce, salt and note nonce, and checks the file matches (run it with
`UPDATE_CARD_VECTORS=1` to rewrite). The applet tests feed the same bytes to
the card's random source and require the same F, commitment, marker and commit
data. Every LMS signature in the tests is checked with Bouncy Castle's RFC 8554
verifier.

On a real card (a sacrificial one with known card manager keys; never lock it):

```
gp --install build/ghostcard.cap
java -cp <host classes>:<bcprov> ghostcard.host.RealCard load      # the H10 tree, about 50 minutes
java -cp <host classes>:<bcprov> ghostcard.host.RealCard certify   # a test certificate
java -cp <host classes>:<bcprov> ghostcard.host.RealCard run 5     # five timed fills, every answer checked
```

## Commands

CLA `80`. Multi-byte numbers are big-endian. Answers longer than the reader
can take come back cut to its Le; the part-reading commands (offset in P1P2,
length in Le) return the rest.

| INS | Command | Allowed | Data | Answer |
| --- | --- | --- | --- | --- |
| `10` | Identify | always | | format 1, phase 1, state 1, card id 16, fill 4, checks left 2, leaves made 2, certificate length 2 |
| `12` | Read certificate | ready | | certificate bytes from P1P2 |
| `14` | Public key | tree made | | the LMS public key, 56 bytes (RFC 8554) |
| `20` | Make | ready, blank, 16+ checks left | amount 12, chain id 8, writer nonce 32, SHA3-256(open code) 32 | fill 4, commitment 32, commit data 430 (unsigned) |
| `22` | Commit data | ready, sealed | | commit data bytes from P1P2 |
| `30` | Check | ready, 1+ check left | challenge 32, optionally a code confirmation 32 | the 194-byte seal statement |
| `32` | Read signature | right after Check | | bytes from P1P2 of the statement's 2,508-byte LMS signature |
| `40` | Open | ready, sealed or opened | open code 20, challenge 32 | fill 4, counter block 16, ciphertext 64, tag 16 |
| `50` | Refill | ready, opened | open code 20 | |
| `60` | Generate | loading | | P1 = leaves to make (1 to 16); answers leaves made, 2 |
| `64` | Write certificate | loading | up to 512 bytes at offset P1P2 | |
| `66` | Finish | loading, tree made | certificate length 2 | |

Status words: `6985` not in this state, `6982` wrong open code, `6984` too few
seal checks (Make needs 16, Check needs 1), `6700` wrong length, `6A86` bad
offset or count, `6A80` bad certificate length.

The applet's AID is `A000000847474341524401` (package `A0000008474743415244`).
The install parameters may give the certificate's room as 2 bytes; the default
is 8,192 bytes, enough for an SLH-DSA-SHA2-128s certificate.

### Phases and states

A new card is **loading**: Generate makes the H10 tree one leaf at a time
(about 3 s a leaf on a J3R180), the issuer writes the certificate, and Finish
makes the card **ready**, blank at fill 0. Loading never comes back: after
Finish, Generate, Write certificate and Finish are refused, so the certificate
cannot change.

A ready card is **blank**, **sealed** or **opened** (state 0, 1, 2), as the
spec's "Card states" says. Make, Open (the first time) and Refill each change
the state in one atomic write together with everything they store or wipe, so
a card pulled away mid-command is left before or after it.

### Make

The card draws 32 bytes of card random, the 16-byte salt and 9 bytes of the
note nonce from its TRNG, in that order. Then, as Ghost's client:

- seed bytes = SHA3-256("ghost-card-key" ‖ card random ‖ writer nonce); the
  Phantom Key's key bytes are `0x20` ‖ seed bytes (a words key);
- s, r, b₀ and the note key are Ghost's tagged SHA3-256 derivations of the key
  bytes (b₀ with index 0); the note's lookup tag is the first 3 bytes of
  SHA3-256(note-tag, note key, number 0) and starts the note nonce;
- F, the commitment and the marker are Ghost's tagged Keccak-256 (0x01
  padding) over COIN_V2 with the empty content and rule;
- the 352-byte version 3 note (number 0, the amount, the salt, an empty
  capsule) is sealed with ChaCha20-Poly1305 under the note key, with the chain
  id and commitment as associated data;
- the commit data is `00 03` ‖ F ‖ salt ‖ note (430 bytes), and the
  commit-data digest is its native SHA-256.

The seed bytes and secrets are wiped from RAM before Make answers.

### Check and its signature

The statement (194 bytes):

| Bytes | Field |
| --- | --- |
| 0..18 | "ghost-card-seal-v1" |
| 18..34 | card id |
| 34 | state |
| 35..39 | fill number |
| 39..47 | chain id |
| 47..59 | amount |
| 59..91 | commitment |
| 91..123 | commit-data digest (SHA-256) |
| 123..155 | marker |
| 155..157 | seal checks left after this one |
| 157..161 | the LMS leaf this signature uses |
| 161 | open code: 0 not asked, 1 right, 2 wrong |
| 162..194 | the receiver's challenge |

A blank card's coin fields (chain id to marker) are zero. The code
confirmation is SHA3-256("ghost-card-code" ‖ SHA3-256(open code) ‖ challenge);
a blank card answers 2 to one.

Check advances the next leaf in an atomic write before anything is signed,
draws the signature's random C, and hashes the statement into the message
digest Q. The signature (LMS_SHA256_M32_H10 with LMOTS_SHA256_N32_W4, 2,508
bytes) is then read with Read signature, in parts of any size: each one-time
chain is computed when it is read, so the card never holds the whole
signature in RAM. The signing context lives only in RAM and only until the
next command other than Read signature (or a power cut), so a leaf is never
used for two messages. The LMS identifier I is the card id; the private chain
values come from a 32-byte seed the card drew at install (RFC 8554,
appendix A).

### Open

On the fill's right code, the card first marks the fill opened (if it was
sealed), then answers the card random and writer nonce (64 bytes) encrypted
with AES-256-CTR under SHA3-256("ghost-card-open-enc" ‖ card id ‖ fill ‖ open
code ‖ challenge), from a fresh 16-byte counter block (incremented as one
128-bit big-endian number), with an AES-CMAC tag under the same with
"ghost-card-open-mac", over "ghost-card-open-v1" ‖ card id ‖ fill ‖ challenge
‖ counter block ‖ ciphertext. An opened card answers Open again with its code.

## On a J3R180

Run on 2026-11-17 over a USB contact reader, which takes answers of at most
256 bytes, so long answers came back in parts:

| Work | Median of 5 fills | Budget (card on a phone) |
| --- | --- | --- |
| Loading: H10 key generation | 51.5 min (3.02 s a leaf) | at the loading station |
| Make (with the commit data's second part) | 2.15 s | 10 s |
| Check, with its signature read | 2.88 s | 3 s |
| Check confirming the open code | 2.89 s | 3 s |
| Open | 0.58 s | 3 s |
| Refill | 0.18 s | 3 s |

Every answer was checked: each LMS signature verified, and each Make's commit
data, commitment and marker recomputed bit for bit from what Open released.

Check is bound by this reader. The card's own work is about 1.7 s: the
statement about 0.1 s and the one-time chains about 1.6 s. The reader moves
about 0.44 ms a byte (2,508 signature bytes take about 1.1 s), against about
0.1 ms a byte over iPhone NFC (docs/j3r180-measurements.md). Over NFC a Check
comes to about 1.7 s × 1.05 + 0.3 s, so about 2.1 s.
